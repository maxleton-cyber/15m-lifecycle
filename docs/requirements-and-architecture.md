# 「15分钟生活圈」智能体检与规划助手 —— 功能需求与技术架构文档

版本：v2.0
适用赛题：开源AI工具赛道 —— 基于地图开放能力的"15分钟生活圈"智能体检与规划助手

---

## 一、项目背景

国家推行"15分钟便民生活圈"建设，要求居民在步行15分钟范围内可获得医疗、教育、购物、养老等基础服务。传统规划依赖人工普查和静态数据，无法反映真实步行可达性（道路非直线、红绿灯、天桥、施工围挡等都会影响实际可达范围），也无法及时发现"服务盲区"。

本项目基于百度地图开放能力（地理编码、POI检索、路径规划），叠加AI智能体与生成能力，开发一款Web应用：输入任意社区/街道中心点坐标（或直接用自然语言提问），自动生成基于真实路网的"15分钟步行等时圈"，统计圈内民生设施覆盖情况，由AI生成可读的诊断报告与改善建议，并自动标注设施匮乏的"灰色区域"。

---

## 二、赛道定位与AI能力设计

赛道要求"直接面向用户的AI应用"，明确列出"行业智能体""AIGC创作工具""数据处理与清洗"等方向。**单纯的地图数据计算+规则判断不构成AI应用**，因此本项目在原有GIS分析能力之上，设计了三层AI能力，使产品定位落在"行业智能体 + AIGC内容生成"的交叉点：

| AI能力模块 | 对应赛道方向 | 作用 |
|---|---|---|
| **Agent编排层** | 行业智能体 | LLM作为决策中枢，通过Function Calling调用地图工具，自主决定检索哪些设施分类、何时重试/降级 |
| **AIGC体检报告生成** | AIGC创作工具 | 将结构化的等时圈/POI/盲区数据转写成有政策建议、可读性强的自然语言报告，而非干巴巴的表格 |
| **多源POI数据清洗** | 数据处理与清洗 | 用LLM辅助做同名店铺去重、品类归一化、连锁品牌识别，解决赛题原文明确要求的"多源POI数据清洗策略" |

**实现方式**：Agent编排层直接在ASP.NET Core后端内实现，不引入额外的第三方Agent平台。具体做法是：把等时圈计算、POI检索、盲区判定等能力定义为标准的Function/Tool Schema，后端封装一个`AgentService`，通过HTTP直连LLM厂商的Chat Completions接口（OpenAI兼容协议，支持Function Calling/Tool Use），由LLM决定调用哪些工具、以什么顺序调用，工具执行结果回传给LLM生成最终的自然语言内容。这样Agent逻辑和地图分析逻辑都在同一个技术栈（C#/.NET）里，减少一套额外系统的部署与运维成本。

## 三、功能需求

### 3.1 核心功能清单

| 编号 | 功能模块 | 说明 |
|---|---|---|
| F1 | 中心点输入 | 支持地址搜索/地图点选/**自然语言输入**（如"帮我看看回龙观东大街适不适合养老"）确定分析对象 |
| F2 | 等时圈生成 | 基于真实步行路径计算15分钟可达范围，生成近似等时圈多边形/热力图 |
| F3 | POI覆盖检索与清洗 | 检索圈内POI，并用AI做多源数据去重、品类归一化 |
| F4 | 盲区识别 | 判定圈内/1公里范围内缺失关键设施（菜市场/药店/小学等）的区域 |
| F5 | **AIGC体检报告生成** | LLM将结构化数据转写为自然语言诊断报告，附政策/居民视角的改善建议 |
| F6 | 可视化 | 地图叠加等时圈、热力图、POI标注；配套雷达图/柱状图；响应式自适应，预留小程序web-view兼容性 |
| F7 | 异常与降级处理 | API异常、限流、配额耗尽时的兜底策略 |
| F8 | 历史记录与对比 | 保存历史分析结果，支持不同社区间横向对比（加分项，非必须） |

> 说明：暂不实现"对话式追问"功能（v2.0曾规划的F6），本期AI能力聚焦在一次性生成AIGC体检报告，不做多轮对话交互。后续如有需要可在此基础上扩展。

### 3.2 功能详细说明

#### F1 中心点输入
- 用户可通过关键字搜索地址（地理编码API转坐标）、地图点选，或直接用自然语言描述（由Agent做一次性意图解析+地理编码工具调用，解析出目标坐标；不涉及多轮对话）
- 支持手动输入经纬度（调试/演示用）

#### F2 等时圈生成（核心难点）
- **不依赖底层路网拓扑数据**，采用官方推荐的"扇形采样 + 空间插值"方案：
  1. 以中心点为原点，按16~24个方向做角度采样（每隔15°~22.5°一个方向）
  2. 每个方向上，用二分查找/步进法调用"步行路线规划"API，寻找"步行时间≈15分钟"对应的距离点
  3. 将各方向的边界点按角度顺序连接，做样条平滑或凸包处理，得到近似等时圈多边形
  4. 多边形叠加到地图上做半透明填色 + 边界线渲染
- 为降低请求量与耗时，优先使用**批量算路（Route Matrix）**接口代替逐点调用步行路线规划
- 采样点距离二分查找建议设置最大迭代次数（如4~5次/方向），避免单次分析请求量失控

#### F3 POI覆盖检索与AI清洗
- 预设设施分类字典，覆盖国家"15分钟生活圈"标准中的核心类目（医疗、教育、购物、养老等）
- 检索结果需二次过滤：剔除等时圈多边形外的点（射线法判定多边形内点）
- **AI清洗环节**（对应赛题"多源POI数据清洗策略"）：
  - 同名/近似名称店铺去重（如"XX药店(建国路店)"与"XX药店建国路分店"应识别为同一实体或明确区分为连锁不同网点）
  - 连锁品牌识别与归类（如"7-Eleven""全家""美宜佳"统一归入"便利店"大类，避免规则字典漏判）
  - 交由LLM做小样本分类/归一化，比纯正则规则更能覆盖长尾命名变体
- 结果统一写入Redis共享缓存（按"中心点坐标+分类"做缓存键），所有用户请求经同一后端转发，命中缓存直接返回，避免重复消耗配额

#### F4 盲区识别
- 规则引擎：对每个分类设定"必须覆盖半径"（如药店1公里、小学1公里），若该半径内查无POI，标记该分类为"盲区"
- 输出结构化盲区列表：`{分类, 是否盲区, 最近同类设施距离, 建议}`

#### F5 AIGC体检报告生成（核心AI能力）
- 输入：等时圈范围、各分类POI统计、盲区列表、覆盖评分等结构化数据
- LLM生成内容包括：
  - 总体诊断摘要（如"该区域养老设施明显不足，建议优先补齐社区食堂"）
  - 分类别点评（结合具体POI数量与距离，给出口语化解读）
  - 改善建议（面向社区规划者的可执行建议，如"建议在XX路口新增便民药店，可覆盖当前盲区约XX户居民"）
- Prompt设计需严格约束LLM只依据传入的结构化数据做总结与建议，不得编造未检索到的设施信息（防止幻觉）

#### F6 可视化
- 地图层：等时圈边界、热力图、POI分类图标、盲区高亮
- 图表层：雷达图（各分类覆盖度评分）、柱状图（各分类POI数量）
- 报告导出：支持生成PDF/图片快照（加分项）
- **响应式自适应**：桌面/平板/手机三档断点自适应布局，移动端优先设计（见3.3节），为后续接入微信小程序web-view预留兼容性

#### F7 异常与降级处理（重点加分项，权重高且工程友好）
- API请求统一封装重试机制（指数退避，最多重试2~3次）
- 触发QPS限流时自动排队重发，控制并发不超过账号QPS上限
- 日配额耗尽时：优先读取Redis共享缓存兜底（缓存对所有用户共享，非用户本地缓存）；若无缓存，降级为"仅展示已获取数据+提示配额受限"
- LLM调用失败/超时时：降级为直接展示结构化数据+固定模板文案，保证核心功能（体检报告）不因AI服务波动而不可用
- POI检索为主要瓶颈接口（个人开发者100次/日），需在架构层面做配额预算控制（见第七节）

### 3.3 移动端与小程序Web-View兼容性设计

前端定位为"独立H5应用"，本期不单独开发小程序原生页面，而是通过响应式设计，让同一套页面既能在桌面浏览器正常使用，也能后续直接被小程序`web-view`组件加载复用，避免重复开发。具体设计要点：

- **响应式断点**：采用移动优先（Mobile First）的CSS设计，建议断点为手机 `<768px`、平板 `768~1024px`、桌面 `>1024px`；地图容器、报告面板、图表等核心组件均需在三档断点下可用，而非仅做桌面端适配
- **交互方式不依赖桌面独有能力**：所有需要hover才能触发的交互（如地图图例的悬浮提示）都要有触屏可用的替代方案（点击/长按），因为小程序webview环境内无鼠标hover事件
- **状态传递不依赖localStorage**：小程序`web-view`内嵌页面的localStorage/cookie行为在Android/iOS上不完全一致，也可能被小程序容器清理。核心参数（中心点坐标、分析任务ID等）优先通过**URL query**传递，而不是依赖页面自身的本地存储做跨会话保留，保证被小程序拉起时能直接通过链接携带参数
- **域名与协议要求**：小程序`web-view`组件加载的页面必须是HTTPS，且域名需提前在小程序后台配置为"业务域名"白名单，这是接入小程序前需要提前规划的部署前提，不是纯前端代码能解决的事
- **地图组件的移动端手势适配**：百度地图JS SDK在移动端webview中的触摸缩放/拖拽手势需要单独测试，与桌面端鼠标滚轮缩放的交互逻辑不同，需要在`MapPanel.vue`里做好两套交互的兼容处理
- **避免使用小程序webview受限的浏览器API**：如某些剪贴板、分享、定位类API在小程序webview容器内表现可能与普通浏览器不一致，涉及此类功能时需做能力检测+降级，不能假设行为与独立浏览器完全相同

> 说明：本期不实现小程序原生壳工程（如新建小程序项目、配置web-view页面），只在H5前端做好响应式与兼容性预留，后续如需接入小程序，只需新增一个小程序壳工程内嵌本页面URL即可，无需改动H5本身的核心逻辑。

## 四、技术架构

### 4.1 技术选型

| 层级 | 技术方案 | 说明 |
|---|---|---|
| 前端 | Vue3 + TypeScript + 百度地图JS API | 响应式布局（移动优先），兼容微信小程序web-view内嵌加载 |
| 图表库 | ECharts | 雷达图、柱状图渲染 |
| 后端 | ASP.NET Core Web API (.NET 8) | 地图API代理层 + AI编排层一体化，隐藏AK密钥，统一限流与缓存 |
| **AI编排层** | **后端内置Agent模块**（`AgentService` + LLM Function Calling） | 直连LLM厂商Chat Completions接口（OpenAI兼容协议，支持Tool Use），不引入独立Agent平台，减少额外服务与调优成本 |
| **异步任务队列** | **`Channel<T>`后台队列 + BackgroundService** | AI报告生成为耗时操作，采用"提交任务→后台Worker按有界并发处理→SSE/轮询取结果"模式，避免同步阻塞、避免高并发打垮LLM API配额 |
| LLM | 自选OpenAI兼容模型（如DeepSeek等） | 负责自然语言理解、报告生成、POI清洗辅助 |
| 缓存/存储 | **Redis** | 服务器端共享缓存，缓存POI/路径规划/LLM生成结果、记录配额消耗；所有用户的请求都经后端统一转发，命中即返回，与用户本地无关 |
| 部署 | Docker + docker-compose | 一键起前后端，满足评审"快速跑通演示"要求 |
| CI/CD | GitHub Actions | 自动构建、格式化检查 |

**数据流说明**：
1. 前端提交坐标或自然语言问题，后端立即返回任务ID（不阻塞连接）
2. 请求进入`Channel<T>`异步队列，由`BackgroundService`按预设的有界并发数（如同时最多3~5个LLM调用，匹配LLM API自身的QPS上限）依次取出处理
3. `AgentService`解析意图，通过Function Calling决定调用哪些地图工具（等时圈计算/POI检索/盲区判定），工具执行结果来自地图工具服务层（内部逻辑，不发网络请求，直接方法调用）
4. 地图工具服务层负责实际的百度地图API调用、Redis缓存读写、限流重试、配额守卫
5. `AgentService`拿到结构化结果后，调用LLM生成自然语言报告，任务状态与结果写入Redis
6. 前端通过SSE推送或轮询`/api/agent/tasks/{id}`获取任务状态与最终结果，同时展示：地图可视化（直接消费结构化数据）+ AI生成的文字报告

### 4.4 AI编排层（后端内置Agent模块）设计

- **架构选择说明**：不引入独立Agent平台（如Dify），原因是自建Dify社区版在工作流并发上有明显瓶颈——它自身的worker进程数、状态持久化开销都是额外的调优负担，且LLM推理本身耗时较长（生成一份报告可能涉及多次工具调用+多轮LLM推理，共5~30秒），并发一高容易在Dify这一层先卡住。改为后端直接集成，Agent逻辑与地图分析逻辑同处一个技术栈，并发控制完全自主可调。
- **Function Calling实现**：`AgentToolRegistry`将等时圈计算、POI检索、盲区判定等地图工具方法包装为标准Function Schema（名称/参数/描述），随本次请求上下文一起传给LLM API；LLM返回的Tool Call由`AgentService`解析并直接调用对应C#方法（进程内调用，无需额外网络跳转），执行结果拼回上下文继续请求LLM，直至生成最终报告（单轮任务内完成，不做多轮对话）
- **异步任务队列设计**（应对"AI处理耗时长、并发易卡住"的核心手段）：
  1. `AgentController`收到请求后，生成任务ID，任务参数写入`AgentTaskQueue`（基于`Channel<T>`），立即返回任务ID（HTTP连接不阻塞等待）
  2. `AgentTaskWorker`作为`BackgroundService`常驻消费队列，内部用`SemaphoreSlim`控制同时处理的任务数（如3~5个），既保护自身服务器资源，也避免超出LLM API自身的并发/QPS限制
  3. 任务处理中的状态（排队中/处理中/已完成/失败）与阶段性结果实时写入Redis
  4. 前端通过SSE（`/api/agent/tasks/{id}/stream`）或短轮询（`/api/agent/tasks/{id}`）获取进度与最终结果，用户可以看到"正在计算等时圈…正在检索设施…正在生成报告…"的渐进式反馈，而不是长时间白屏等待
- **Agent Prompt核心约束**：
  - 只能基于工具返回的结构化数据做总结/建议，禁止编造未出现的设施或数据
  - 涉及位置/距离/数量的表述必须与工具返回数据一致（避免"幻觉"影响可信度）
  - 工具调用失败时如实告知用户，不得虚构结果
- **处理流程**（对应Worker内部逻辑）：
  1. 输入解析（坐标/地址/自然语言 → 标准坐标）
  2. 等时圈计算（调用工具方法）
  3. POI检索+清洗（调用工具方法 + LLM清洗）
  4. 盲区判定（规则计算）
  5. 报告生成（LLM生成自然语言内容）

## 五、核心算法说明

### 5.1 等时圈生成算法（扇形采样法）

```
输入：中心点坐标 (lat, lng)，目标时间 T=15分钟，采样方向数 N=20
输出：等时圈多边形顶点列表

1. for angle in [0, 360/N, 2*360/N, ..., 360-360/N]:
     low = 500米, high = 1800米（步行15分钟经验上限，约合4~5km/h*15min）
     repeat 最多5次（二分查找）:
        mid = (low+high)/2
        target_point = 沿angle方向、距中心mid米处的坐标
        实际步行时间 = 调用步行路线规划(中心点 -> target_point)
        if 实际步行时间 > T: high = mid
        else: low = mid
     该方向边界点 = low对应坐标
2. 将N个边界点按角度顺序连接 -> 多边形
3. 可选：对多边形做样条平滑，避免锯齿感
```

> 优化建议：用"批量算路"接口一次性提交N个方向候选点，减少请求轮次，同时更好控制QPS。

### 5.2 盲区识别算法

```
输入：等时圈多边形，POI分类字典（含每类"必须覆盖半径"）
输出：盲区列表

for category in 分类字典:
    pois = 检索(中心点, category, 半径=max(等时圈外接半径, 必须覆盖半径))
    圈内pois = 过滤(pois, 落在等时圈多边形内)
    if 圈内pois为空:
        最近同类设施 = 检索(中心点, category, 半径=3km) 中最近一个
        标记为盲区，记录最近距离
    else:
        计算覆盖评分 = f(数量, 平均距离)
```

### 5.3 覆盖评分公式（示例，可调）

```
score = min(100, 40 * log(1 + POI数量) + 60 * (1 - 平均距离/必须覆盖半径))
```

### 5.4 AI辅助POI清洗流程

```
输入：某分类下检索到的原始POI列表（含名称、坐标、地址）
输出：去重、归一化后的POI列表

1. 按坐标做初步空间聚类（如50米内视为候选重复）
2. 对候选重复组，将名称交给LLM做实体判断：
   "以下几个地点名称是否指同一家门店？[名称列表]" → 是/否 + 合并建议
3. 对连锁品牌类目模糊的POI（如未标准分类的小店），
   用LLM做品类归一化："XX便利店"应归入"购物-便利店"而非"其他"
4. 输出清洗后的POI列表 + 清洗日志（供技术报告展示清洗前后对比）
```

### 5.5 AIGC报告生成Prompt设计要点

- 输入数据结构化传入（JSON），明确要求"仅基于以下数据生成报告，不得添加未提及的设施信息"
- 输出格式约束：分"总体摘要 / 分类点评 / 改善建议"三段式，便于前端渲染
- 建议加一层输出校验：报告中提到的数字（如POI数量、距离）与原始数据做一致性核对，不一致则触发重新生成或降级为模板文案

## 六、异常与降级策略汇总

| 故障场景 | 降级策略 |
|---|---|
| 百度地图API限流/超时 | 指数退避重试，优先读Redis共享缓存，超出配额则提示"当日分析次数已用完" |
| POI检索配额耗尽（瓶颈接口） | 优先使用Redis共享缓存数据，报告中标注"部分数据来自缓存" |
| LLM服务不可用/超时 | 降级为固定模板文案 + 展示原始结构化数据，保证核心功能可用 |
| LLM输出与原始数据不一致（疑似幻觉） | 触发重新生成一次；仍不一致则丢弃AI文本，仅展示结构化数据 |

## 七、API配额预算

根据百度地图开放平台"开发者权益"页面（个人开发者额度），本项目关键接口配额如下：

| 接口 | 个人开发者配额(次/日) | 本项目单次分析预计消耗 |
|---|---|---|
| 步行路线规划(轻量) | 5,000 | ~20次（20方向采样） |
| 批量算路 | 5,000 | 建议优先用它替代逐点步行规划 |
| 地理编码 | 5,000 | 1次（地址转坐标） |
| **地点检索（POI）** | **100（瓶颈）** | 8~20次（多分类+分页） |

**结论**：POI检索是全链路瓶颈，个人开发者账号每天大约只能支撑5~10次完整分析。

**应对策略**：
1. Redis共享缓存：以`(中心点坐标, 分类)`为key缓存POI检索结果，所有用户请求命中同一份缓存
2. 配额预算器（`QuotaGuardService`）：每日重置计数，前端`QuotaBanner`实时展示剩余额度
3. 降级策略：配额不足时优先使用Redis缓存数据
4. 开发/演示阶段建议主办方申请企业试用版Key，或提前准备好2~3个示例社区的完整缓存数据用于演示
